# 开发流程

> 每次开发必须遵守。开工/收尾逐项打勾，缺一不可。
> GitHub 仓库：`git@github.com:howtio/espidf.git`

---

## 1. 开工前（逐项打勾，跳过 = 不允许写代码）

```
□ 1. 读 docs/00_总体施工文档.md      ← 知道当前骨架状态
□ 2. 读 docs/01_架构说明.md           ← 知道模块边界和 Queue 协议
□ 3. 读 docs/04_开发计划.md           ← 知道当前 Phase 和剩余任务
□ 4. 读 docs/DEV_PROGRESS.md          ← 知道上次做到哪、遗留问题
□ 5. 读 docs/LOG.md                   ← 看历史施工记录

□ 6. 检查 Git
      git branch --show-current       ← 当前分支（正常是 main）
      git status                      ← 工作区必须干净

□ 7. 创建远端备份（硬门槛）
      git checkout main
      git checkout -b backup/YYYYMMDD-<本轮描述>
      git push -u origin backup/YYYYMMDD-<本轮描述>
      git checkout main
      没有远端备份 = 不允许写代码

□ 8. 列出开发计划（等用户确认后再动手）
      ┌──────────────────────────────────────────┐
      │  本次目标：（一句话）                      │
      │  涉及文件：（具体到路径）                    │
      │  改动方式：（新建/修改/重构）                │
      │  验收标准：（怎么算完成）                    │
      │  非目标：（明确不碰什么）                    │
      │  模块接口：（对外接口是否有变化）              │
      └──────────────────────────────────────────┘
      发给用户确认，用户说"开始"再动手写代码。

□ 9. 确认起点干净
      idf.py build                     ← 确保当前代码可编译
```

---

## 2. 开发（渐进增量）

```text
先通最小链路 → 再补异常处理 → 再优化性能 → 最后美化 UI
```

每个小功能完成后：
- `idf.py build` 确认可编译
- 如果条件允许 `idf.py flash monitor` 实机验证

### 解耦开发原则

```
1. 每个 component 只暴露 .hpp 接口，实现藏在 .cpp
2. 模块间不直接 include 对方 .cpp 或内部头文件
3. 新增功能优先在现有 component 内扩展，不轻易增加新 component
4. 跨模块通信只走 Queue，不走全局变量
5. 每个模块的 "对外接口" 变更必须在 docs/06_模块接口规范.md 中更新
```

### 渐进开发原则

```
1. 每个 Phase 只做一件事，出问题立刻知道范围
2. Phase 内再拆小步，每步可独立编译验证
3. 同一时间只改一个 component 的核心逻辑
4. 上一个 Phase 稳定后再开始下一个
```

## 3. 收尾（逐项打勾，缺一 ≠ 完成）

```
□ 1. 编译
      idf.py build                     ← 必须编译通过（0 error, 0 warning）

□ 2. 更新文档
      docs/LOG.md                      ← 施工日志，必须追加
      docs/DEV_PROGRESS.md             ← 开发进度，必须更新
      docs/00_总体施工文档.md          ← 如有文件结构变化
      docs/01_架构说明.md              ← 如有模块边界变化
      docs/06_模块接口规范.md           ← 如有接口变更

□ 3. 提交
      git add <具体文件1> <具体文件2>    ← 禁止 git add -A / git add .
      git commit -m "$(cat <<'EOF'
      <type>: <简短描述>

      Phase：<当前阶段>
      改动：
      - <模块>：<做了什么>
      编译：通过

      Co-Authored-By: Claude <noreply@anthropic.com>
      EOF
      )"

□ 4. 推送
      git push origin main
      没 push = 本轮不算完成

□ 5. 输出总结
      编译结果：（通过/失败）
      提交号：
      备份分支名+提交号：
      回滚判断：（需要/不需要）
```

## 4. 回滚规则

### 什么时候回滚
- 编译失败且快速修复成本 > 本轮收益
- 变更污染了不相关模块
- 架构边界被破坏（Audio 直接调了 Display、Touch 直接调了 I2S）
- Queue 协议被绕过
- PSRAM/SRAM 分配策略被破坏

### 回滚顺序（从轻到重）

| 级别 | 命令 | 场景 |
|------|------|------|
| 1 文件级 | `git checkout -- <文件>` | 只撤销具体文件 |
| 2 提交级 | `git revert <commit>` | 撤销整笔提交 |
| 3 分支级 | `git reset --hard backup/<日期-描述>` | 回到备份分支 |

### 回滚后必须
```
□ git status           ← 确认状态
□ idf.py build         ← 确认编译通过
□ 更新 docs/LOG.md     ← 记录回滚原因
□ 输出：回滚了什么、为什么、复测结果
```

## 5. Git 规范

| 项目 | 值 |
|------|-----|
| 仓库 | `git@github.com:howtio/espidf.git` |
| 默认分支 | `main` |
| 备份分支 | `backup/<YYYYMMDD>-<描述>` |
| 功能分支 | `feat/<描述>` |
| 修复分支 | `fix/<描述>` |

### 提交 type

```text
feat / fix / refactor / docs / test / chore
```

### 不进 Git

```text
build/  sdkconfig  sdkconfig.old
*.bin  *.elf  *.map  *.o
dependencies.lock  managed_components/
```

## 6. 验证命令

```bash
# 编译
idf.py build

# 烧录 + 监视
idf.py flash monitor

# 检查固件大小
idf.py size

# 检查各组件大小
idf.py size-components
```

---

## 7. 禁止事项

- 未编译就声称完成
- 跳过备份直接开发
- `git add -A` 或 `git add .`
- 全仓乱改不相关模块
- 绕过 App FSM 直接发 Queue 消息
- 在模块间用全局变量通信
- 把"未测试"写成"已验证"
- 没 push 说完成了
- 在 SDK 默认配置里写本地路径
